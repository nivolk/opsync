# Устройство opsync и принятые решения

Для тех, кто дорабатывает opsync. Пользователям — [README](../README.md).

## Задача

Агент (Claude Code, Codex, Cursor, Claude Desktop) работает в репозитории проекта и ведёт его задачи в OpenProject
так же, как вёл бы человек: берёт задачи спринта, двигает их по доске по мере работы, пишет в
ленту, что сделано, закрывает после приёмки. Инструмент не знает ни о каком проекте —
проект подключается конфигом.

Вырос из реального проекта: агент вёл спринт по колонкам «Новое → В процессе → В
тестировании → закрыто» вместе с коммитами и приёмкой; разовый код смены статусов стал
командами `start/review/done`.

## Слои

```
opsync/skill/SKILL.md               процесс: когда и что делать (для агента); setup копирует
                                    его агентам, MCP отдаёт его разделы как instructions
opsync/cli.py                       команды и вывод (для человека и агента, --json)
opsync/mcp_server.py                те же операции как MCP-инструменты (клиенты без shell)
opsync/setup.py                     доступ и подключение агентов, хуки Claude Code
opsync/hooks.py, rules.py           хуки (сводка при старте, подсказка после коммита);
                                    блок правил в AGENTS.md / CLAUDE.md
opsync/tasks.py                     ведение задач: ref → id, статус, комментарий, лента,
                                    доска, время, создание, сводка context
opsync/report.py, gitinfo.py        состояние проекта для команды; OP#N в коммитах
opsync/apply.py, plan.py, catalog.py   YAML-план → OpenProject
opsync/schedule.py, pull.py, planedit.py   даты; сервер → план; правка YAML без потерь
opsync/config.py, client.py         настройки; HTTP (авторизация, ошибки, пагинация)
```

`tasks.py` не зависит от CLI: его вызывают и CLI, и MCP-сервер.

## Решения

**CLI + скилл; MCP — для клиентов без shell.** CLI работает и у человека в терминале, и у агента через Bash,
его вывод прозрачен, отлаживается без клиента MCP. Скилл даёт агенту процесс — то, чего MCP
не даёт вовсе: описание инструментов говорит «как вызвать», но не «когда переводить в
review и почему не закрывать самому». Для клиентов без shell (Claude Desktop) —
`opsync mcp`: тонкая обёртка над `Tasks`, правила процесса — разделы того же SKILL.md.
Готовые MCP для OpenProject (см. [`API.md`](API.md)) — обёртки над API без плана и процесса;
встроенный в OpenProject — только Enterprise.

**Конфиг ищется вверх от текущего каталога**, как `.git` или `pyproject.toml`: агент может
работать в подкаталоге. Доступ — отдельно от проекта (`~/.config/opsync/.env`), чтобы токен
не попадал в репозитории проектов.

**Этапы, а не статусы.** Команды называются по смыслу (`start`, `review`, `done`), а имена
статусов задаёт конфиг: у каждого экземпляра OpenProject они свои, в том числе по регистру
(«закрыто» строчными). `doctor` проверяет, что все этапы указывают на существующие статусы.

**Идемпотентность.** Повторный `start` или `done` не ошибка: агент может не помнить, что уже
сделал, а пересъезд статуса туда-обратно засоряет историю. Комментарий пишется всегда.

**Комментарий — перед сменой статуса, переход проверяется заранее.** OpenProject склеивает
изменения одного автора за несколько минут в одну запись ленты: смена статуса присоединяется
к предыдущей записи. При порядке «статус, потом комментарий» комментарий review оказывался
рядом с переходом в «закрыто» (найдено на песочнице 08.10.2026). Комментарий в теле PATCH
сервер молча игнорирует. Поэтому: форма (`/work_packages/{id}/form`) → комментарий → PATCH;
запрещённый переход отказывает до записи, с перечнем допустимых статусов.

**Статус не принадлежит плану.** `apply` задаёт статус только при создании задачи. Дальше
статус ведут люди и `start/review/done`; повторный `apply` его не трогает (до 07.10.2026
трогал — откатывал задачи в «Новое», найдено при обобщении).

**Состояние плана — рядом с планом** (`<каталог плана>/.state/<name>.json`), а не в
текущем каталоге: иначе запуск из репозитория проекта не нашёл бы соответствие key → id и
сопоставлял задачи по теме, с риском дублей после переименования.

**План — в репозитории проекта** (`.openproject/plan.yaml`),
вместе с файлом состояния: план описывает задачи проекта и меняется вместе с его кодом, а
состояние без коммита теряется на другой машине.

**Спринты — в плане, создаются руками**. С 17.3 спринты —
отдельные объекты, и API v3 их только читает. Вместо обхода API (браузер, Rails-консоль)
план описывает спринты с датами, а `apply` сверяет их с сервером и выдаёт точный список
ручных действий. Даты спринтов из плана нужны планировщику и до создания на сервере.

**Даты считает opsync, а не OpenProject**.
Автопланирование OpenProject знает связи и длительность, но не загрузку исполнителя и не
границы спринта. Планировщик (`schedule.py`) — чистая функция плана и календаря, без
«сегодня»: иначе каждый `apply` сдвигал бы даты. Включается флагом `calendar.schedule`,
чтобы не поменять даты существующих планов молча. Закреплённые даты не трогает, перегрузку
от них только показывает: переставлять договорённые сроки — решение человека.

**Перенос между спринтами правит и план.** Спринт задачи — поле плана: поменять его только
на сервере значит, что следующий `apply` вернёт задачу назад. `carry` и `pull` правят YAML
через ruamel.yaml (комментарии и форматирование сохраняются байт в байт) — только они
пишут в план.

**Новая задача сразу попадает в план.** Работа, найденная по ходу, должна быть видна
команде сразу, а не после правки YAML и `apply`, — иначе она оседает только в локальном
трекере. `opsync new` создаёт задачу на сервере и тут же дописывает её в план (`- key: …`
с полями или `- id: N`, как `pull --adopt`): план остаётся полным описанием проекта, а
следующий `apply` ничего не меняет. Описание обязательно — его читают люди без контекста
сессии. Даты не ставятся: это решение человека или планировщика.

**Ссылка на задачу — id или key плана.** Key стабилен и читаем (`be-reset-token`), id —
то, что видно на доске (`#100`). Тема в качестве ссылки не принимается: неоднозначна.

**Прозрачность — главная цель.** Человек, открыв OpenProject, должен понять, что сделано,
что в работе, что мешает и что дальше, не спрашивая того, кто работал с агентом. Отсюда:
ход работы — заметками (`note`) между start и review, блокер — состоянием задачи (`block`) с
причиной, а не только словами в чате; картина проекта — статусом и пояснением на обзоре
проекта (`report`), там, куда команда и так смотрит.

**Комментарии пишутся для людей.** Агент склонен к отчётам «для машины»: списки файлов,
вывод тестов. Правила и примеры — в скилле; `Tasks.comment` грубо проверяет текст и пишет
замечание (запись не останавливает — следующий комментарий агент напишет проще). Похожее на
секрет не записывается вовсе: лента видна всей команде и рассылается письмами.

**Агент всегда в контексте.** Скилл срабатывает, только когда агент о нём вспомнил. Поэтому
три слоя: хук SessionStart (Claude Code) кладёт сводку `context` в начало сессии, хук после
`git commit` подсказывает следующий шаг по задаче, а блок в AGENTS.md / CLAUDE.md держит
правило для агентов без хуков. Хуки только читают и молчат при ошибках: сессия важнее
сводки. Хук коммита срабатывает на каждый Bash — до проверки «это git commit» модуль
ничего тяжёлого не импортирует (~20 мс).

**Этап blocked необязателен.** Подходящего статуса может не быть в экземпляре; тогда этап
не настраивается, `block` объясняет, какую строку добавить, а `doctor` подсказывает статус.
Старые `.openproject.yaml` работают без изменений.

**off_track сам не ставится.** В русском интерфейсе он подписан «Приостановлен» — для
команды это звучит как остановка проекта. `report` ставит «по плану» или «под угрозой»;
«отстаёт» — решение человека (`--health off_track`).

## Чего нет и почему

- Чтения локального трекера (`docs/TASKS.md` и т.п.) — форматы у проектов разные; поле
  `tracker` — подсказка агенту, сопоставление делает он.
- Настройки категорий, спринтов, типов, workflow — в API OpenProject этого нет; `apply`
  выводит список ручных настроек. Закрытие спринта — тоже в интерфейсе.

## Где проверено

OpenProject 17.8 Community с модулем Backlogs (спринты — `/projects/{id}/sprints`), русский
интерфейс. Запись проверяется на отдельном проекте-песочнице; тесты — без сети
(`tests/conftest.py`, `FakeClient`).
