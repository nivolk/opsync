# Задачи в OpenProject через opsync

`opsync` — CLI поверх OpenProject API. Доступ настраивается один раз (`opsync setup`),
привязка репозитория — файл `.openproject.yaml` (ищется вверх от текущего каталога).

Цель — чтобы человек, открыв OpenProject, без вопросов понял, что сделано, что в работе,
что мешает и что дальше. Всё, что ты делаешь по задаче, должно быть видно в её ленте.

## Перед началом

1. `opsync context` — проект, спринт, твои задачи в работе / на проверке / в ожидании с
   последним комментарием, что дальше, риски. С хуками Claude Code эта сводка уже есть в
   начале сессии — повторять не нужно.
2. Ошибка доступа — `opsync doctor`. Нет доступа — попросить пользователя выполнить в
   терминале `opsync setup`. Нет `.openproject.yaml` — `opsync init` (выбор проекта из
   списка) или, если пользователь назвал проект, `opsync init --project <id>`.
3. Если в репозитории есть свои правила ведения задач (AGENTS.md, CLAUDE.md, локальный
   трекер) — они главнее этого скилла. Локальный трекер и OpenProject ведутся вместе:
   рядом с задачей трекера — `(OP #N)`.

## Команды

| Нужно | Команда |
|---|---|
| С чего начать | `opsync context` |
| Состояние спринта | `opsync board` (текущий; `--sprint "Спринт 2"`) — колонки, часы, риски |
| Задачи | `opsync list` (`--sprint S`, `--mine`, `--all` — с закрытыми, `--json`) |
| Найти, что уже делали | `opsync search "<слова>"` (`--all` — с закрытыми) |
| Задача целиком | `opsync show <ref>` — описание, связи, последние записи ленты (`--history 0` — все) |
| Взял в работу | `opsync start <ref> -m "<что и в каком порядке делаю>"` |
| Ход работы | `opsync note <ref> -m "<что сделано, что дальше>"` — без смены статуса и писем |
| Ждёт чего-то извне | `opsync block <ref> -m "<что мешает, от кого ждём>"`; снято — `opsync unblock <ref>` |
| Сделано, ждёт проверки | `opsync review <ref> -m "<что изменилось, как проверить>"` |
| Принято | `opsync done <ref> -m "<кем и как проверено>"` |
| Вернуть в работу | `opsync reopen <ref> -m "<почему>"` |
| Новая работа | `opsync new "<тема>" -m "<зачем, когда готово>" [--type Ошибка] [--sprint S] [--parent ref] [--estimate 4h] [--key k] [--mine]` |
| Уточнить описание | `opsync describe <ref> -m "<текст>"` |
| Другой статус | `opsync status <ref> "<имя статуса>"` |
| Комментарий | `opsync comment <ref> "<текст>"` |
| Списать время | `opsync log <ref> 2h -m "<что делал>"` или `--spent 2h` у этапа |
| Состояние проекта | `opsync report --summary "<главное>"` → показать → `--publish` |
| Конец спринта | `opsync carry "<спринт>" --dry-run` → показать → `opsync carry "<спринт>"` |

`ref` — `123`, `#123` или key из плана проекта. Повтор команды безопасен: задача уже в нужном
статусе — статус не меняется. Комментарий передавать через `-m` той же командой: так он
попадает в одну запись ленты со сменой статуса. `--no-notify` — без писем участникам.

Отказ «переход … запрещён workflow. Можно: …» — ничего не записано. Не обходить через
промежуточные статусы: показать пользователю допустимые переходы и спросить. `block`
отвечает «этап blocked не настроен» — сказать пользователю, какую строку добавить в
`.openproject.yaml` (ошибка её называет), а пока написать блокер `note`.

## Жизненный цикл задачи

1. **Разбор.** `opsync context` / `opsync board` — что в работе и где риски; `opsync show`
   по задаче — описание и что о ней уже писали. Найти соответствие в локальном трекере и в
   коде. Предложить пользователю порядок работ и согласовать **до** смены статусов.
2. **start** — когда начинаешь конкретную задачу, а не все сразу; одна задача в работе за
   раз, если пользователь не попросил иначе. В `-m` — коротко, что и в каком порядке
   делаешь. Если из описания непонятно, что считать готовым, — предложить текст и
   дополнить `opsync describe`.
3. **Коммиты** — с `OP#<номер>` в сообщении. Так коммит виден у задачи (интеграции
   OpenProject с GitLab и GitHub), а `review` сам подставит его хеш.
4. **Ход работы** — `opsync note` при заметном шаге и обязательно в конце сессии, если
   задача не готова: что сделано, что дальше. Человек, открывший задачу завтра, должен
   понять, где она.
5. **block** — если ждёшь кого-то или чего-то вне своей работы (доступ, ответ, решение):
   что мешает и от кого ждёшь. Сняли блокер — `unblock`.
6. **review** — сразу после коммита, прошедшего проверки проекта: что изменилось для
   пользователя и как проверить. Не отправлять на проверку незакоммиченное или с красными
   проверками.
7. **done** — только после приёмки: пользователь подтвердил, или вторая сторона отчиталась и
   ты сверил её отчёт. Самостоятельно, «потому что тесты зелёные», — не закрывать.
8. **reopen** — если приёмка нашла дефект; причину — в комментарий.

**Новая работа.** Нашёл проблему или работу вне текущей задачи — не чинить молча и не
оставлять только в локальном трекере: сказать пользователю и с его согласия завести
`opsync new` (ошибка — `--type` с типом ошибки проекта). Описание — зачем и когда готово,
для людей. Если у проекта есть план, `new` сам допишет задачу в него — закоммитить план.

**Картина проекта.** По просьбе пользователя или в конце спринта — `opsync report`: собрать
факты, дописать «Главное» (`--summary`: 2–3 предложения — что важного произошло и что из
этого следует), показать пользователю, после согласия — `--publish` (статус и пояснение на
обзоре проекта), в конце спринта ещё `--news`.

## Комментарии

Лента задачи — то, по чему команда понимает, что происходит. Пиши так, как обычный
разработчик пишет коллеге, который не видел сессию: на языке проекта, простыми словами,
1–4 предложения. Что сделано — по смыслу для пользователя или системы, а не по файлам; что
осталось или мешает; как проверить. Коммит — одной ссылкой в конце, если он есть.

Не писать: списки файлов и классов, логи и вывод тестов, внутренние имена из кода без
пояснения, «реализовал функционал», упоминания AI и инструментов, секреты (токены, пароли,
внутренние адреса). `opsync` предупредит о длинном или «машинном» комментарии и откажется
записать похожее на секрет.

| Когда | Плохо | Хорошо |
|---|---|---|
| start | «Начинаю работу над задачей.» | «Берусь. Сначала поправлю проверку прав, потом добавлю кнопку в карточку.» |
| по ходу | «Обновлены UserService.cs, UserController.cs, UserTests.cs, Migration_42.cs» | «Удаление на сервере готово, осталась кнопка в интерфейсе — доделаю завтра.» |
| block | «Blocked.» | «Жду от заказчика пример файла выгрузки — без него не проверить разбор. Спросил в чате 14.10.» |
| review | «Реализован функционал удаления. Все тесты прошли (142 passed).» | «Администратор теперь может удалить вложение у заявки в любом статусе. Проверить: открыть закрытую заявку → вложения → удалить. Коммит 2af79e8.» |
| done | «Закрыто.» | «Проверила Анна на тестовом стенде, замечаний нет.» |
| reopen | «Баг.» | «На стенде удаление падает, если файл уже удалён с диска — возвращаю в работу.» |

## План проекта (YAML)

Если в `.openproject.yaml` задан `plan`, состав задач, сроки, спринты и иерархия описаны в
нём (формат — `references/plan.md` рядом с этим файлом). Порядок правки:

1. Изменить YAML. Новым задачам — оценку (`estimate`), спринт и связи `follows`.
2. `opsync schedule` (если в плане `calendar.schedule: true`) и `opsync apply --dry-run` —
   показать пользователю, что будет создано и изменено.
3. `opsync apply` — только после его согласия. Спринты, которых нет на сервере, `apply`
   перечислит: их создаёт пользователь в интерфейсе OpenProject.
4. Закоммитить план вместе с его каталогом `.state/`.

Статусы в плане руками не править: `opsync pull` переносит их из OpenProject (на сервер не
пишет), после него закоммитить план. Задачи, заведённые в OpenProject руками, `pull`
перечислит; брать их в план (`--adopt`) — только по просьбе пользователя.

## Что требует подтверждения пользователя

- Закрытие (`done`) и переоткрытие задач, если пользователь не поручил это явно.
- Смена статуса больше чем трёх задач за раз.
- `opsync new` (создание задач), `opsync carry` и `opsync apply` без `--dry-run`,
  создание проектов.
- `opsync report --publish` и `--news` — их видит вся команда.
- Любая правка дат и сроков (`start`, `due`, `date`, `calendar.schedule`). Перегрузку,
  которую показывают `board` и `schedule`, — показать, но сроки самому не двигать.
- Любое действие с задачами, которые не относятся к текущей работе.

Работа с задачей, которую ты сейчас делаешь (start, note, block, review), — часть работы,
если пользователь поручил вести задачи в OpenProject; отдельно не спрашивать.

## Ошибки

`opsync` сам подсказывает следующий шаг в тексте ошибки — следовать ему. Если команды
`opsync` нет — попросить пользователя установить: `uv tool install` по инструкции его
команды, затем `opsync setup`.
